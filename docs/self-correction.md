# 自行比对与自行纠错（多轮修复）

本文回答三个问题：**现在的管线能不能自己发现自己错了、能不能自己改、还需要人做多少**。
所有数字都来自可复现的测试；真实识别准确率（CER）仍未测量，这一点在最后一节单独说明。

## 1. 现状评估：能做什么、缺什么

改造前的管线是**一次性**的：

| 能力 | 改造前 | 现在 |
| --- | --- | --- |
| 双引擎独立识别 | 有 | 有 |
| 逐字符对齐 + 冲突定位 | 有 | 有 |
| 风险打分（分歧/变体/标点/缺行/低置信） | 有 | 有 |
| 裁决（自动 / VLM / 人工） | 有，但**只判一次** | 有，且**可以再来一轮** |
| 分歧行的二次读取 | 无（只能进人工队列） | **有**：隔离、留白、放大后重读 |
| 多读者一致性判定 | 无（只有"两个引擎是否相同"） | **有**：`consensus()`，≥2 个独立读者 |
| 轮次停止条件 | 无 | **有**：预算 / 尝试耗尽 / 已全部解决 |
| 导出前"整体质量"报告 | 无（只有未解决计数） | **有**：`progress()`，自动接受率 |
| 成品 EPUB 回读比对 | 有（只比对"导出 vs 决策层"） | 有，见 §6 的边界 |

结论：**改造前没有实现多轮自行纠错**。它只能"发现问题"，不能"再试一次"，所以人的工作量
等于全部未解决项；而分歧项往往只是裁切太紧、笔画挤在一起，重读一次就能定。

## 2. 为什么不能直接"把 EPUB 和 PDF 逐字比对"

这是最容易走错的一步，值得写清楚：

- **EPUB 里的字就是 OCR 认定的字。** 把它和 PDF 原件比对，需要有"原件里本来是什么字"的
  独立来源；PDF 是扫描图，没有文本层，所以**唯一的真值是像素**。
- **"把文本渲染回图片再和扫描图做像素差"不可行。** 中文字形、字体、字距、行距、扫描畸变
  都会产生巨大差异；这个差值度量的是排版而不是识别，噪声远大于信号。
- 所以真正的"逐字比对"只能是：**让另一套独立的读者去读同一块像素，再比较它们的结论。**
  这正是本项目的双引擎架构已经做的事——缺的只是"读不好就换个方式再读，并承认多数派"。

## 3. 实现：一轮修复做的事

`scribeforge.pipeline.rounds`：

1. **选出该读的**：所有还没有接受决策、且不是页眉页脚（furniture）的配对，按风险分从高到低；
2. **重新裁切**：从原页重新裁出这一行，**留白更宽、放大倍数更高**（第 n 次尝试用
   `padding + 0.02·n`、`scale = 1 + n`，均有上限）。同一个裁切配同一个引擎只会得到同一段
   文本，所以必须改变**输入**；
3. **重读并落库**：每个配置的读者各读一次，作为 `engine_runs.scope = "pair:<n>"` 的
   **区域证据**落库。它不会被误当成"这一页的最新识别结果"（`latest_engine_run` 只认
   整页运行），因此对齐、目录/页码和导出组装都不会被污染；
4. **判定**（`scribeforge.domain.consensus`）：把所有独立读数放在一起——两个整页引擎读数、
   本轮的区域重读、以及（配置了 VLM 时）**对放大后的裁切重新求助视觉模型**的那一次读数；
5. **接受或留白**：某个文本得到 **≥2 个独立读者**支持、且严格多于次高票组，才成为该配对的
   新决策（`decisions` 追加一行，引用全部支持读数的 evidence id）；否则保持未解决，等下一轮
   或人工。

判定规则的取舍（都写成了回归测试）：

| 规则 | 原因 |
| --- | --- |
| 空读数、自报不确定的读数**不投票** | 缺文本不是"同意空字符串"；不确定不等于反对票 |
| 一个字面文本需要 **≥2 个读者** | 单个读者的自信不是独立证据（issue #76） |
| 变体字差异算**同一个读数**，但接受的字面保持原样 | 一致性是折叠后比较，导出绝不改写字形 |
| 两组票数**相同时不裁决** | 加读者是为了减少歧义，不是为了制造赢家 |
| 同一轮里同时接受"整页引擎 + 区域重读" | 重读给出的是**不同输入**上的独立判断 |

## 4. 什么时候停

- **预算**：`--repair-rounds N`（默认 0 = 关闭；实际使用建议 2）；
- **尝试耗尽**：同一个配对最多重读 `max_attempts_per_pair`（默认 3）次；之后它被标记为
  `skipped`，交给人工——继续用同样方式重读只是烧钱；
- **没有可读的**：要么全部解决，要么剩下的都耗尽尝试。

每轮都产出 `RoundReport`（读了几个、解决几个、仍有歧义几个、耗尽几个、因预算延后几个），
`scribeforge repair --json` 直接输出；`process --repair-rounds 2` 则在首页跑完后自动继续。

## 5. 人工工作量：从"逐行"到"看两个数"

`progress()` 给出这本书当前的状态：

```
accepted without a person: 812 automatic, 96 by vision model, 3 by a human
still open: 11 pair(s), 4 of them high risk, 2 a machine may not accept (auto-acceptance 99.0%)
```

这行的用途就是用户描述的判断：**自动接受率足够高、未解决项集中在低风险** → 只需抽查；
**未解决项多、或高风险项没降下来** → 再来一轮 `repair`，或在同一台机器上换读者
（第三引擎、VLM）再跑。

`a machine may not accept` 是[自动接受闸门](./acceptance-gate.md)的口径：这些配对不是
"两个引擎读得不一样"（那需要人来裁决），而是"机器根本没有资格接受"（替换字符、
控制字符、置信度过低）—— 对它们正确的动作是**换一次输入再读**，而不是在同一条
读数上纠结。

导出闸门没有放松：只要还有一个配对没有接受决策，`export` 仍然拒绝导出（exit 2）。
"自动纠错"不等于"自动编造"。

## 6. 边界：这套东西**不能**做什么

1. **看不到"两个引擎都没读出来的行"**。区域重读只重读**已对齐的行**；整页漏行属于覆盖率
   问题，需要"整页重读 + 行数/行位比对"（下一节 L2）。这是当前最大的盲区。
2. **共同错误无法靠重读修复**。若两套引擎把同一个字读成同一个错字，多数派会一致地错；
   只有**换一个真正独立的读者**（第三引擎、VLM、或人）才可能发现。
3. **轮次不是无限预算**。默认 3 次尝试、每轮 40 个配对；一本 500 页的书如果风险项集中在
   少数页，宁可提高 `--repair-max-pairs`，也不要无脑加轮次。
4. **成品 EPUB 只做"是否忠实于决策层"的校验**（`export_check`：逐块读回、字符不丢）。
   它证明"导出没写错"，不证明"识别没读错"——后者只能由 §2 的独立读者机制来回答。
5. **没有真实 CER**。本节所有能力都用确定性假引擎在测试里验证（引擎返回什么完全可控，
   可以精确构造"分歧→重读→收敛"与"重读仍不一致"两条路径）；真实引擎在真实扫描件上的
   收益率（多少配对会被一轮重读解决）**尚未测量**，因为本环境没有 GPU 也没有模型权重。

## 7. 下一步路线（按性价比排序）

| 层 | 内容 | 为什么 |
| --- | --- | --- |
| L1（已完成） | 区域重读 + 共识 + 轮次 + 进度报告 | 把"分歧"从人工队列变成可自动解决的多数问题 |
| L2 | **整页重读覆盖率比对**：第三个读者（如 Surya 版面 + PaddleOCR）重读整页，比较行数、行位与字符数，专门抓"漏行/多行/串行" | 现在的盲区就是两个引擎同时漏掉的行 |
| L3 | **VLM 整页回读**：把整页（或半页）交给视觉模型，按行返回文本，与决策层逐行比对，仅把不一致行送入 L1 | 视觉模型擅长"看结构"，可发现拼接错误与顺序错误 |
| L4 | **质量闸门自动化**：把 `progress()` 的自动接受率、高风险未解决数、行覆盖率先验写成阈值，未达标时自动再跑一轮并报告 | 用户描述的"整体不达标就再跑一轮"的自动化版本 |
| L5 | **成品回读**：对已导出的 EPUB 重新抽取文本，反向对齐回页面，报告"哪一页哪一行可疑" | 面向"给我一份 EPUB 体检报告"的场景 |

L2 需要第三个引擎（`paddleocr-vl` / `surya` 的 worker 骨架已在仓库里，见
[docs/technology-route.md](./technology-route.md)），L3 需要本地 VLM 端点，两者都受本环境
无 GPU 限制，属于"代码可写、收益待测"。

## 8. 命令

```bash
# 首页处理时顺便修 2 轮（推荐）
scribeforge process book.pdf --repair-rounds 2

# 对已处理过的 store 再跑：不重新做 OCR，只重读分歧行
scribeforge repair --store book.scribeforge --repair-rounds 2

# 只看现在能不能导出、还差多少
scribeforge repair --store book.scribeforge --repair-rounds 1 --json
scribeforge export --store book.scribeforge --out book.epub
```

退出码：`0` 全部配对已接受（可以导出），`1` 仍有配对需要人（导出会被拒绝），`2` 无法运行
（store/引擎/参数问题）。

## 9. 相关 issue

- **#76（视觉模型自报确定即可自动采用第三种文本）**：已修。现在 VLM 读数必须与至少一个
  引擎读数一致（字面或变体折叠后一致）才会被接受，否则记为 `vlm_uncorroborated` 并留给
  人工；重读轮里的视觉读数是"一个读者"，同样不能单独定案。
- **#84（可信导出以文本行为主）**：相关。段落重建见 [docs/paragraphs.md](./paragraphs.md)；
  本轮的"逐行证据"正是段落重建所依赖的输入。
- **#75（高风险行可能被双引擎一致规则直接放行）**：**仍未修**。双引擎一致仍会被自动接受；
  修复轮不会改变这一点（一致即无分歧，没有可重读的对象）。这是风险闸门的设计问题，
  应在 `risk` 层解决。
- **#86 / #77 / #82**：与"区域重读"相邻但不阻塞：块标签/置信度、子进程超时、页图哈希。
