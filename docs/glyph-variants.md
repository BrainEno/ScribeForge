# 繁简 / 异体字规范化层（issue #88）

## 1. 原则：只改变"比较"，不改变"文本"

两个 OCR 引擎读同一行扫描件，很常见的差异并不是读法不同，而是**字形选择不同**：
一个输出 `爲`、另一个 `為`；一个 `鴉`、另一个 `鸦`；一个全角、一个半角。

如果把这种差异当作实质分歧，会产生两个连锁伤害：

1. 真正的风险信号被稀释——复核队列塞满"其实两边都对"的条目；
2. 复核者被训练成"看到差异就点通过"，等到真的分歧出现时已经麻木。

因此本项目的硬规则是：

> **规范化永远不重写已接受文本。**
> 导出、决策、证据都保留引擎实际输出与人工实际选择的字符。

规范化只服务于三处：

| 用途 | 位置 |
| --- | --- |
| 行对齐时的相似度（决定哪些行配对） | `domain/alignment.py::_text_similarity` |
| 风险评分（区分"字形差异"与"读法分歧"） | `domain/risk.py::assess_page` |
| 决策裁定（字形一致即视为独立一致） | `domain/decisions.py::adjudicate_pair` |

## 2. 折叠方式

```
NFKC（兼容形式：全角→半角、兼容表意文字）
  → 查表折叠（繁简 + 异体字）
  → 标点宽度折叠（，→, 「→" …）
  → 去空白 + casefold（旧书里常见的拉丁片段 "IBM"/"V." 大小写差异）
```

`fold_chars()` 是**轻折叠**（保留空格与标点，只做 NFKC + 异体字），供需要可读输出
的场合使用；`fold_for_comparison()` 是**重折叠**（比较键），永不用于生成给读者的文本。

## 3. 词表是显式人工整理的，不是 OpenCC

- 当前 334 个组、520 个字符映射（`_VARIANT_GROUP_DATA`），覆盖中文旧书扫描里常见的
  繁简对与异体字对（`羣/群`、`峯/峰`、`裏/裡`、`著/着`、`祕/秘`、`歎/嘆`…）。
- 加载时校验**矛盾映射**：同一字符若被两个组指向不同规范形，直接抛 `RuntimeError`，
  不允许"随便挑一个"——错误合并会把两个不同的字当成同一个，那是静默的文本损坏。
- 不完整的词表在这里是**安全**的：漏掉一组只会让比较更保守（继续走人工复核），
  不会造成错误合并。而 OpenCC 那类完整方案的引入属于 #90 技术路线的一部分。

## 4. 行为变化

### 4.1 对齐

`_text_similarity` 改用折叠后相似度。过去引擎甲输出繁体、乙输出简体时，同一行相似度
可能低到 0.3，行只能靠垂直距离配对，跨列/串行配对概率上升。现在这种行相似度为 1.0。

### 4.2 风险

新增 `RiskReason.VARIANT_DISAGREEMENT`：

| 情形 | 权重 | 是否进入复核队列（阈值 0.35） |
| --- | --- | --- |
| 存在实质替换 `TEXT_DISAGREEMENT` | 0.45 | 是 |
| 仅字形差异 `VARIANT_DISAGREEMENT` | 0.10 | 否（但记录在证据里） |

注意：只有当**所有**替换冲突都是字形差异时才降权；混合情形按实质分歧处理，即"就高不就低"。

### 4.3 裁定

`adjudicate_pair` 新增 `variant_agreement` 分支：两引擎文本折叠后相同 → 自动接受
**主引擎的字面文本**（不折叠、不改写），`rationale="variant_agreement"` 写入决策证据。
若只有一侧有文本，仍然判 `missing_engine_text`，不会被折叠"补全"。

## 5. 测试覆盖

- 繁简/异体折叠、NFKC 兼容形式、标点与空白折叠；
- 词表矛盾的静态校验；
- `is_variant_only_difference` 对"相同文本"返回 False（相同不是差异）；
- 对齐：跨字形引擎的行仍按文本配对，相似度 ≥ 0.99；
- 风险：字形差异 < 0.35 且带 `VARIANT_DISAGREEMENT`；实质替换 ≥ 0.45；
- 裁定：字形一致自动接受且保留主引擎文本；真实分歧仍需复核。

## 6. 已知边界

- 词表覆盖不足时行为保守，但也不会"学习"新异体字。
- 未处理**古今字/通假字**（如 `說/悦`、`女/汝`）：那是注释层面的问题，
  不能靠字形折叠解决，属于校勘工作流（#90）。
- 未处理竖排/旋转导致的字符切分错误——那属于 #86 的版面与 #79 的阅读顺序。
