# 古籍 / 旧版书扫描件支持评估与开发路线

- 评估日期：2026-10-28
- 评估对象：`BrainEno/ScribeForge` @ `c10150a`
- 基准数据：`benchmark/V..pdf`（托马斯·品钦《V.》叶华年译本，译林出版社 2008，562 页，读秀/超星扫描）
- 基准语料：`benchmark/corpus/v/`（6 页，含人工转写参照文本）

> 本文是**首要开发目标的正式记录**。结论：ScribeForge 当前的工程骨架、
> 证据链与导出层质量足以承载这个目标，但**现有技术路线尚不足以处理排版复杂、
> 非标准化、非高清的古籍与旧版书扫描**。第 6 节把缺口按 P0/P1/P2 排序，
> 第 7 节给出经过核实的免费开源技术路线建议，第 8 节给出阶段计划。
>
> **时点说明：**第 1–9 节记录 2026-10-28 的审查快照；后续实现状态见第 10 节，
> 以第 10 节为当前状态。不要把旧版“现状”段落当成当前实现清单。

---

## 1. 结论摘要

| 判断 | 结果 |
| --- | --- |
| 能处理 500–800 页大型 PDF 的结构性流程？ | **能**。分页处理、断点续跑、单页失败隔离均实测通过 |
| 能处理清晰现代印刷扫描（如本次基准 PDF）？ | **结构上能，精度未测**。双引擎分歧与复核链路可跑通，但真实 CER/WER 至今没有可复现的实测值（见 §4.3） |
| 能处理排版复杂的古籍 / 旧版书扫描？ | **不能**。存在 4 项 P0 缺口，见第 6 节 |
| 技术路线是否需要更换？ | **不需要推倒重来，需要补层**。管线抽象是对的；缺的是预处理层、竖排/版式层和结构化层 |

关键结论逐条：

1. **架构不是瓶颈。** 引擎被适配层隔离，域模型与 OCR 实现解耦，
   每个阶段可独立重跑。这恰好是后续接入 Surya / PaddleOCR-VL /
   古籍专用模型所需要的形状。无需重写。
2. **瓶颈是"输入侧"和"版面侧"。** 代码把 pdfium 渲染出的原图**直接**
   交给 OCR 引擎，没有任何去歪斜、去阴影、二值化、去噪；对齐算法又
   **假设横排从左到右**。这两点对古籍是致命的。
3. **本次审查发现并已修复 2 个真实缺陷**（第 5 节），两者都会在
   真实扫描件上直接把整页判为失败或让全书变慢。这说明"
   真实扫描件测试"这件事本身此前是缺失的。
4. **基准里没有可复现的真实 OCR 数字。** `benchmark_report.md` 曾经列出过一次
   4 页运行的 CER/WER，但那次运行的语料从未入库，任何人（包括维护者）都无法
   复现它，因此不能作为证据。本次提交了语料与一键运行方法，但本沙箱无 GPU、
   无模型下载通道，仍无法产出真实 A/B/C/D 分数。见 §4.3。

## 2. 审查范围与方法

1. 通读全部 `src/scribeforge` 模块（64 个文件）、`docs/`、测试套件与 CI 配置。
2. 实测 `PdfPageSource` + `import_source` 在真实 PDF 上的导入开销。
3. 用确定性合成引擎驱动**真实**编排、决策、组装与导出链路，测量 562 页规模下的
   时延、SQLite 体积与内存（合成引擎明确不是 OCR，仅测周边机制）。
4. 用真实 PDF 页验证几何契约、对齐算法复杂度、以及跨引擎脏数据的鲁棒性。
5. 对 6 个真实页面做人工转写，建立基准语料。
6. 检索并核实当前（2026）可用的免费开源文档理解/OCR 路线。

## 4. 实测数据

### 4.1 基准 PDF 特征

| 属性 | 值 |
| --- | --- |
| 物理页数 | 562 |
| 页面尺寸 | 595.3 × 894.6 pt → 2481 × 3728 px @ 300 DPI |
| 来源 | `Creator: DuXiu/SuperStar`，`Producer: AnnasArchive` |
| 平均亮度 / 暗像素比 | 240.1 / 255，4.73% |
| 单页 PNG 均值 | ≈ 1072 KB |
| 全书资产估算 | ≈ 590 MB |
| 扫描质量 | 较好：白底黑字、无可见歪斜、少量噪点 |

**该 PDF 不属于典型古籍**：它是干净的黑白现代印刷体，简体横排。所以它适合做
"基线回归语料"，**不足以验证古籍能力**。这一点对结论很重要 —— 即使它全绿，
也不能证明古文能力。

### 4.2 规模实测（真实测量，非估算）

导入（真实 PDF 光栅化，走生产 `PdfPageSource` + `import_source`）：

| 指标 | 值 |
| --- | --- |
| 40 页 @300DPI 耗时 | 11.5 s |
| 每页耗时 | 0.287 s |
| 吞吐 | ≈ 209 页/分钟 |
| 每页资产 | 1072 KB |
| 峰值 RSS | 117 MB |

562 页编排 + 组装 + 导出（确定性合成引擎，**非 OCR**）：

| 指标 | 值 |
| --- | --- |
| 562 页编排耗时 | 54.9 s（0.098 s/页）|
| 组装（assembly） | 3.1 s |
| EPUB 导出 | 0.06 s（198 KB）|
| DOCX 导出 | 0.08 s（39 KB）|
| SQLite 体积 | 66.8 MB |
| 决策条数 | 14050 |
| 峰值 RSS | 130 MB |

**解读：**

- 存储与内存**不是问题**。800 页书籍约需 850 MB 资产 + 95 MB 数据库。
- 真正的耗时会被 OCR 引擎主导。按仓库既有基准（MinerU 9.5 页/分、
  PaddleOCR 4.0 页/分）串行双引擎推算，562 页约 **2 小时以上**，
  800 页约 **3 小时以上**。这是纯串行、无并发、无页面跳过的结果。
- 导入阶段每页都要重新打开 PDF 并渲染（`PdfPageSource.render_page`
  每次 `PdfDocument(...)`）。功能上稳健，但 562 页意味着 562 次文件打开。

### 4.3 关于真实 OCR 分数的诚实说明

本仓库的 `benchmark_report.md` 至今是 pending。本次提交了：

- 6 页可复现语料（`benchmark/corpus/v/`），带人工转写参照文本；
- 语料与工具的一致性测试；
- `benchmark/analysis/scale_harness.py` 规模测量工具。

但在当前沙箱中**无法产出真实 A/B/C/D 分数**：没有 GPU，且模型托管域名
（paddlepaddle.org.cn / huggingface.co / modelscope）不在可访问范围内。
维护者有 GPU 的机器上执行：

```bash
scribeforge setup                     # 一次性安装 MinerU + PaddleOCR 运行环境

  --out benchmark/benchmark_report.md --include-pipeline
```

即可得到真实数字。**在该命令产出结果之前，任何关于准确率的结论都只能是
结构性的，不能是数值性的。** 本文档不填造数字。

## 5. 本次审查发现并修复的缺陷

两个缺陷都是"真实扫描件才会触发"的类型，且都会造成整页或全书的
功能性失败。按 `AGENTS.md` 的 TDD 要求，先写失败测试再改实现。

### 5.1 归一化几何越界会导致整页被拒（已修复）

`workers/protocol.py:normalize_polygon` 把像素多边形直接除以页面尺寸，
不做钳制。真实扫描件常见以下输入：

| 输入 | 修复前 | 后果 |
| --- | --- | --- |
| 块多边形越过页面右/下边缘 | 产出 `width=1.2` | `BoundingBox` 抛 `ValueError` |
| 去歪斜后出现负坐标 | 产出 `x=-0.01` | `BoundingBox` 抛 `ValueError` |
| 块框与页面同大且带噪声 | `x+w=1.0000001` | 浮点溢出被拒 |

`BoundingBox.__post_init__` 拒绝 0..1 之外的值是对的（它保护证据几何），
但**归一化层不该产出这种值**。现在改为在像素空间钳制到 `[0, width]` /
`[0, height]` 后再归一化。

同一类问题在 `workers/mineru_worker.py:_box`（MinerU 的归一化 bbox）
也存在，已一并钳制。

影响面：所有 PaddleOCR / MinerU 输出。对干净印刷页多数时候侥幸正常，
对边缘有裁切、去歪斜、书脊阴影的旧书扫描几乎必然触发。

### 5.2 对齐算法对稠密页面是 O(n²) 文本比较（已修复）

`domain/alignment.py:_match_primary_lines` 对**每一对**行先算
`SequenceMatcher` 相似度，再判断垂直距离是否超限。也就是说，
垂直距离这一廉价条件被放在了最贵的计算之后。

实测（修复前，80 行/页）：

| 行数 | 修复前 | 修复后 | 提升 |
| --- | ---: | ---: | ---: |
| 20 | 67 ms | 7.9 ms | 8.5× |
| 40 | 269 ms | 17.6 ms | 15× |
| 60 | 587 ms | 28.0 ms | 21× |
| 80 | 1018 ms | 37.2 ms | **27×** |

古籍、竖排、双栏页面的"行"更多（每页 40–100 个检测框很常见），
所以这个差距在目标场景下会放大。修复方式是先按几何距离过滤，
只对通过筛选的候选计算相似度；**匹配结果与修复前完全一致**
（现有全局最优贪心测试仍然通过）。

## 6. 缺口详析与新优先级

### P0 —— 不解决就无法宣称支持古籍/旧版书

#### P0-1 图像预处理层缺失

现状：`adapters/pdf_pages.py` 渲染后**直接**返回 PNG 字节；
`pipeline/orchestrator.py` 把它原样交给引擎。

后果：

- 倾斜（旧书扫描的常态）→ 文本框错切 → 对齐失败 → 大量假冲突
- 书脊阴影 / 光照不均 → 单侧文字丢失
- 泛黄、褪色、低对比度 → 识别率断崖
- 印章、水印、装订孔、透印（bleed-through）→ 幻读
- 无二值化/降噪/分辨率自适应

建议落点：新增 `domain/preprocess.py`（纯域层，可测）+ `adapters/image_preprocess.py`
（OpenCV/scikit-image 实现），在 IMPORT 与 PRIMARY_OCR 之间插入 `PREPROCESS`
阶段，并把预处理产物作为新的、不可变的证据层（不要覆盖原始渲染）。
参数必须持久化，保证可复现与可追溯。

#### P0-2 竖排 / 从右到左不支持

现状：`alignment._center_y` 用 Y 轴中心距离配对，
`line.box` 语义是水平行；`risk._candidate_crop` 用行框并集。

后果：竖排文本（古籍主流）行与列颠倒，配对与阅读顺序全错。
这不是"精度下降"，是**语义错误**。

建议落点：

1. 页面级方向检测（`horizontal-lr` / `vertical-rl`），写入 `pages` 表；
2. 对齐层按方向选择主轴（竖排用 X 轴、从右到左排序）；
3. 阅读顺序抽取独立成层，不要隐含在对齐里；
4. 导出层按方向决定段落拼接规则（竖排不加行内空格）。

#### P0-3 复杂版面分析完全依赖 MinerU

现状：`mineru_worker` 以 `--tier basic` 调 `mineru-kit parse`，
把**每个 block 整体当成一行**（`extract_lines`），且 tokens 恒为空。

后果：

- 多栏 / 双栏 / 图文混排 / 表格 / 眉批旁批 无法自行处理
- 段落内换行信息丢失（block 级 bbox 冒充行级 bbox）
- 无字符级置信度 → `risk.LOW_CONFIDENCE` 永远不触发
- 对齐用的是块框，crop 会覆盖整段，VLM 复核区域过大

建议落点：Worker 应输出**块 + 行 + token** 三级几何，并保留 block 类型标签
（正文/标题/脚注/图表/页眉页脚）。这需要扩展 `docs/ocr-worker-contract.md`
的 schema（版本 2），属于契约变更，须同步更新文档与测试。

#### P0-4 章节结构与页码模型缺失

实测发现（本次语料即为例证）：该 PDF 有**三段各自独立编号**的内容 ——
出版说明（页 1–2）、译者序（页 1 起）、正文（页 1 起），中间还有空白分隔页。
物理页序 ≠ 印刷页码。

现状：`pages` 表只有物理 `page_index`；EPUB nav 只有 `Page N`；
DOCX 只有分页符。没有任何章节概念。

后果：

- EPUB 目录是"Page 1…Page 562"，不可用
- 首行"第一章"被当成普通正文段落
- 空白页、封面页、版权页同样进入 OCR 与人工复核队列
- 导出必须等到全书每一对都解决，包括纯粹的装饰页

建议落点：新增 `page_role`（cover/blank/toc/body/front-matter/footnote-page）
与 `chapter` 概念；导出时按章节生成 nav/h 标题；页码映射记录印刷页码。

### P1 —— 明显影响可用性与成品质量

#### P1-1 繁简与异体字

古籍几乎全为繁体且大量异体字。当前文本层**不做任何转换**。
建议：新增独立的规范化层（`domain/normalize.py`），基于 OpenCC
提供"保留原字 / 转简体 / 异体归正"三档策略，**默认不转换**（符合
"绝不静默改写原文"的项目铁律），转换结果作为派生层单独记录。

#### P1-2 页面分类与跳过

封面、空白、插图、版权页应被识别并走不同策略：空白页直接标记 verified-empty，
插图页记录为 figure 而非待复核文本。这能显著削减人工复核量。

#### P1-3 页眉页脚 / 页码去除

当前不做。它们会作为正文行进入对齐与导出，既污染文本又制造假冲突。

### P2 —— 效率与规模化

- `PdfPageSource.render_page` 每页重开文档；800 页 = 800 次打开。
- 串行双引擎无并发；可安全并行（页级独立）。
- 无 OCR 结果缓存；同一页重跑要重算。
- 导出/组装对 800 页仍是秒级，不是瓶颈，可暂不动。

## 7. 免费开源技术路线调研（2026 年 10 月核实）

前提：**必须免费、开源、可本地部署**；目标是繁体/竖排/异体字/
复杂版面的中文古籍与旧版书。

### 7.1 候选清单

| 方案 | 许可 | 体量 | 中文/竖排 | 版式能力 | 部署门槛 | 定位 |
| --- | --- | --- | --- | --- | --- | --- |
| **PaddleOCR / PP-StructureV3** | Apache-2.0 | 小（PP-OCRv6 检测识别数十 MB 级） | **强**，中日英混排 | 版面+表格+公式 | CPU 可跑，GPU 更好 | 建议保留为主力识别引擎 |
| **PaddleOCR-VL (0.9B)** | Apache-2.0 | 0.9B | **强**，含竖排/手写/旧文档 | 端到端结构化 | 需 GPU 较友好 | 建议作为古籍主引擎候选 |
| **Surya / Marker** | Apache-2.0（权重 OpenRAIL-M） | 650M | 90+ 语种 | 版面+阅读顺序+表格 | GPU 或 CPU(llama.cpp) | 版式/阅读顺序的第二意见 |
| **Kraken** | Apache-2.0 | 小 | 需自训模型 | **专为古籍分栏设计** | CPU | 古籍分栏与自训字形 |
| **CnOCR** | Apache-2.0 | 小 | 支持**竖排**识别 | 行级 | CPU | 竖排轻量补位 |
| **Indra OCR** | 见仓库 | ONNX，CPU | 支持竖排（转 90° 读列） | 行+块+阅读顺序 | 纯 CPU，极快 | 高吞吐初筛/二次意见 |
| **docTR / Docling** | Apache-2.0 / MIT | 中 | 一般 | 版面+阅读顺序+表格 | CPU 可跑 | 结构化输出参考 |
| **Chandra / dots.ocr / DeepSeek-OCR / olmOCR** | 各异（Chandra 9B、dots 3B、DeepSeek 3B、olmOCR 8B） | 大 | 中英较强 | 端到端 VLM | 需较大显存 | 可选 VLM 复核，不作默认 |
| **TongGuOCR**（学术，2026-08） | 论文/权重待查 | — | **专为中文历史文献** | 版面感知分块+生僻字词表 | 需 GPU | 跟踪，暂不投产 |
| **Tesseract `chi_tra_vert`** | Apache-2.0 | 极小 | 繁体竖排有专用模型 | 弱（无版面） | 纯 CPU | 仅作对照基线 |

### 7.2 建议

**不建议更换整条路线，建议"补两层 + 换一个主引擎"。**

1. **保留 ScribeForge 的双引擎分歧 → 风险 → 复核 → 决策骨架。**
   这是本仓库真正的资产，任何 OCR 模型都不提供它。
2. **主识别引擎升级为 PaddleOCR-VL（0.9B）**，理由：同属 Paddle 生态，
   现有 `paddle_worker` 与 runtime planner 改动最小；Apache-2.0；
   对繁体、竖排、旧文档、手写有明确优化；0.9B 在消费级显卡上可跑。
   同时保留 PP-OCRv6 检测识别作为"廉价第一意见"，形成
   **快引擎 + 强引擎** 的分歧组合，比现在"两个中等引擎"更有信息量。
3. **引入 Surya 作为版面/阅读顺序的独立第二意见**（不是识别引擎）。
   它的价值在于"页面结构"而非"字形"，正好补 P0-3。
4. **竖排专项：CnOCR / Indra OCR 作为第三意见。**
   两者都明确支持竖排，成本低，适合做交叉验证。
5. **古籍分栏：评估 Kraken 的分栏能力**，或至少在预处理层实现
   "分栏切分后再逐栏识别"，避免跨栏串行。
6. **图像预处理用 OpenCV + scikit-image**（二者均为 BSD/Apache 系宽松许可），
   不要自研算法。
7. **VLM 复核层保持不变**（OpenAI 兼容接口），只是可选用更强的本地
   Qwen-VL 类模型；但**不要把 VLM 当作主识别**——它会静默改写原文，
   与项目"证据级、不改写"的铁律冲突。VLM 只应回答"这一小块到底是什么字"。

### 7.3 不建议的方向

- ❌ 直接用某个 9B 级 VLM 端到端出全书 Markdown：不可溯源、会幻觉、
  与证据链模型冲突。
- ❌ 依赖云端 OCR API：违背 local-first。
- ❌ 为古籍重新自研 OCR 模型：成本远超收益，开源现成方案已足够。

### 10.1 P0-2 竖排/从右到左：已完成的部分

原缺陷：`alignment._center_y` 用 Y 轴中心距离配对。竖排文本的行是**列**，
同一块正文的所有列共享几乎相同的 Y 范围，用 Y 轴配对等于随机配对；
阅读顺序也写死为自上而下、从左到右。

现在（`domain/direction.py` + `domain/alignment.py`）：

| 环节 | 处理方式 |
| --- | --- |
| 方向检测 | `detect_page_direction()`：行框长宽比 ≥ 1.6 的行占比 ≥ 0.6 且 ≥ 3 行时判为竖排，再按首末列中心 x 判 RL/LR。证据不足返回 `None`（"没有意见"，不是"横排"） |
| 方向裁决 | `resolve_page_direction()`：引擎声明优先（竖排声明 > 横排声明），其次几何，最后默认 `horizontal-lr` |
| 主副轴 | `LineAlignment.cross_axis_distance`：横排是 Y 向间距，竖排是列间 X 向间距；配对轴随之切换 |
| 阅读顺序 | `HORIZONTAL_LR`=(y,x)、`HORIZONTAL_RL`=(y,-x)、`VERTICAL_RL`=(-x,y)、`VERTICAL_LR`=(x,y)；未配对行也参与排序并占据其阅读位置 |
| 证据持久化 | schema v7：`verification_runs.direction` 记录对齐所用方向；`engine_runs.direction` 为 NULL 表示引擎**没有**声明方向（不是声明了横排） |

关键设计决定：`PageOCRResult.direction` 的默认值不能当声明用。v1 worker 无法
上报方向，若把默认 `horizontal-lr` 当作声明，几何检测就永远得不到机会，而 v1
worker 会被静默当成"已看过页面并判定为横排"。因此新增 `direction_declared`
标志，仅当 worker 真的给了 `direction` 字段才置位；库里以 NULL 表示未声明。

**代码路径已有实现和真实页回归，但尚未通过能力门槛。** `benchmark/corpus/guji/`
中的 3 页真实刻本已用于 oracle 全链路测试；测试覆盖几何方向检测、按列配对、从右到左
阅读顺序及 EPUB/DOCX 的列拼接。Oracle 强制识别误差为零，因此这些结果只能证明
管线没有丢字或反序，不能证明真实 OCR 的识别准确率。真实引擎是否能稳定按列输出、
不同版式下方向检测的误判率，以及竖排书的端到端 CER 仍待测量。

**仍阻塞宣称的三件事**：

1. 真实竖排/繁体基准语料尚未达 R4：目前 3 页（要求 ≥20 页），转写为单次校订，
   且双行夹注等复杂版面样本不足，见 §10.3；
2. 真实 OCR 引擎输出与方向检测仍需在有模型权重的机器上验证，不能用 Oracle 结果替代；
3. 端到端**识别准确率 CER**仍未实测（管线自身的损失地板为 0，见 §10.2）。

因此 README 的门槛声明保持不变：**竖排古籍不可宣称支持**。

### 10.2 端到端 CER：先测出管线的“损失地板”

原缺口：仓库里只有像素级测量（分离度、残余歪斜），没有任何识别准确率数字。
在无 GPU、无模型下载通道的环境里，凭空写一个 CER 数值是不诚实的；能诚实做的
是把“管线自己会不会吃掉文本”变成可复现的实测值。

新增 `benchmark/oracle.py` + `scribeforge benchmark --oracle-ceiling`：两个
**回放真值**的 oracle 引擎走完整的对齐 → 风险 → 裁决 → 组装链路。识别误差被人为
置零，所以报告里剩下的任何 CER 都只能来自管线自身的处理（页眉页脚剔除、配对、
裁决、导出拼接）；配对分歧也就完全可控（两引擎同源，36/36 全接受）。

在真实基准语料（`benchmark/corpus/v/`，6 页）上的实测结果：

| 变体 | 页数 | 平均 CER | 缺失行 | 多余行 | 阅读顺序错误 | 已接受配对 | 未解决配对 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `oracle`（引擎层） | 6 | **0.0000** | 0 | 0 | 0 | — | — |
| `oracle-ceiling`（全链路） | 6 | **0.0000** | 0 | 0 | 0 | 36 | 0 |

结论：**在这 6 页上，管线的文本损失为 0**——页眉页脚、页码、脚注剔除与裁决都没有
吃掉正文，竖排以外的一切环节不构成 CER 下限问题。这同时证明 CER 计算链路本身
是通的（`0.0000` 不是“没算”，引擎层与全链路两条路径都跑了真实页面）。

顺带修掉一个度量缺陷：真值文件末尾的换行曾被算作一个插入字符，使每页凭空 +1
个错误，把 0.5% 量级的 CER 相对抬高约 20%。现在评分前统一走 `scoring_text()`
（CRLF 归一、行尾空白裁剪、文首文末空行裁剪，**文内**空行保留）。

**这仍然不是识别准确率。** 真实 CER 需要一个装了 MinerU / PaddleOCR(-VL) /
Surya 权重的机器：

```bash
python -m scribeforge.cli benchmark \
  --manifest benchmark/corpus/v/manifest.json \
  --out benchmark/benchmark_report.md \
  --engine mineru --engine paddleocr --include-pipeline
```

这条命令与 `--oracle-ceiling` 走同一套评分与渲染代码，跑完就是真数字。R5 的验收
标准（每引擎/每组合 CER，横排竖排分开）因此只差机器与语料，不缺代码。

## 11. 已知风险

1. **基准语料代表性不足。** 除 6 页现代简体横排外，当前只有 3 页繁体竖排古籍；
   仍达不到 R4 的规模与版面覆盖要求。
2. **参照文本非双重校订。** `corpus/v` 与 `corpus/guji` 的 manifest 均显式标为
   `single-pass`，并在 `ground_truth_note` 记录限制。可作回归基线，不能当作金标准。
3. **版权。** `benchmark/V..pdf` 是受版权保护的出版物译本。它已在仓库中，
   但新增古籍语料时必须使用公有领域或已获授权材料。
4. **真实 OCR 数字仍然缺失。** 在有人跑出
   `benchmark_report.md` 之前，所有准确率表述都必须标注为"未测量"。
